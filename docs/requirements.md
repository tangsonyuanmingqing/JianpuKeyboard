# Jianpu Keyboard — Product Requirements

## 1. 文档目的

本文档定义 Jianpu Keyboard 当前版本的产品需求，作为 Cursor 开发、测试和后续迭代的主要产品依据。

当前版本以已经确认的实际界面和产品方向为准。

核心目标：

> 将数字简谱文字转换为键盘字母简谱，并尽可能保持歌词、音符和谱面结构的对应关系。

---

## 2. 产品定位

Jianpu Keyboard 是一个跨平台的数字简谱处理工具。

核心业务链路：

```text
数字简谱文字 + 可选歌词
    ↓
点击「转换」
    ↓
Parse
    ↓
Lyric Alignment
    ↓
Validate
    ↓
Mapping
    ↓
Render
    ↓
字母简谱 + 歌词输出
```

未来可以继续扩展图片识谱、播放、自动操作、MIDI、导出等能力。

---

## 3. 目标平台

长期目标平台：

- Windows
- macOS
- Android
- iOS

核心简谱转换能力应尽量使用共享代码实现。

自动按键、鼠标、全局快捷键等能力属于平台相关的可选能力，不要求四个平台完全一致。

---

## 4. V1 目标

V1 的目标是完成一个稳定、易用的：

> **数字简谱文字 → 键盘字母简谱文字**

工具。

用户可以：

1. 输入数字简谱。
2. 可选输入歌词。
3. 点击「转换」。
4. 查看转换后的字母简谱。
5. 点击「复制」。
6. 点击「清空」重新输入。

编辑数字简谱或歌词时，不得自动执行完整转换。只有点击「转换」后才执行解析、校验、歌词对齐、映射和渲染。

---

## 5. 当前实际 UI

### 5.1 数字简谱输入区

标签：

```text
数字简谱
```

用户直接输入数字简谱文本，例如：

```text
3 3 3 4 5 | 3 2 2
1 1 1 2 3 | 3 7, 7,
```

### 5.2 歌词输入区

标签：

```text
歌词（可选）
```

歌词不是强制输入。

支持直接输入连续中文歌词，例如：

```text
黑黑的天空低垂
亮亮的繁星相随
```

也支持已经使用空格分隔的歌词，例如：

```text
黑 黑 的 天 空 低 垂
```

程序内部应统一进行歌词 token 化和对齐。

### 5.3 操作按钮

当前提供：

```text
转换
复制
清空
```

「转换」为手动触发。用户编辑输入时不更新输出、错误或警告；点击「转换」后才执行完整转换链路。

V1 不加入播放、自动按键、图片导入、MIDI、宏等未来功能按钮。

### 5.4 输出区

标签：

```text
字母简谱
```

输出转换后的字母简谱。

带歌词时，应尽量保持字母与歌词在视觉上的对应关系。

示例：

```text
D D D F G | D S S
黑 黑 的 天 空 | 低 垂
```

## 7. V1 简谱语法

### 7.1 中音

```text
1 2 3 4 5 6 7
```

### 7.2 高音

使用单引号：

```text
1' 2' 3' 4' 5' 6' 7'
```

### 7.3 低音

使用逗号：

```text
1, 2, 3, 4, 5, 6, 7,
```

### 7.4 休止符

```text
0
```

规则：

- 不转换成键盘字母。
- 不消耗歌词。
- 必须保留在输出中。

示例：

```text
3 0 4
```

输出：

```text
D 0 F
```

### 7.5 延音符

```text
-
```

表示延续前一个音。

规则：

- 不是新的音符。
- 不消耗新的歌词。
- 必须保留在输出中。

示例：

```text
7 - -
```

输出：

```text
J - -
```

### 7.6 小节线

```text
|
```

必须保留。不消费歌词。

示例：

```text
3 4 5 | 6 7
```

输出：

```text
D F G | H J
```

## 8. 歌词需求

歌词是 V1 的重要能力。

### 8.1 歌词可选

没有歌词时，转换仍然必须正常完成。

### 8.2 连续中文歌词

用户可以直接输入：

```text
黑黑的天空低垂
```

默认必须按中文字符拆分：

```text
黑 黑 的 天 空 低 垂
```

### 8.3 已分隔歌词

用户也可以输入：

```text
黑 黑 的 天 空 低 垂
```

程序必须能够识别。

### 8.4 歌词对应

默认规则：

> 一个歌词 token 对应一个可消费的 Note。

V1 使用**全局顺序对齐**，不按行重置：

1. 所有简谱行中的可消费 `Note` 按原始顺序组成一个连续音符序列。
2. 所有歌词行中的歌词 token 按原始顺序组成一个连续歌词序列。
3. 两者从头到尾依次对应。
4. 换行不重置歌词对齐。

以下 token 不消费歌词：

- Hold `-`
- Rest `0`
- MeasureBar `|`

例如：

```text
3 4 5
我 爱 你
```

对应：

```text
D F G
我 爱 你
```

跨行时同样按全局顺序对应，而不是每行重新从头匹配：

```text
谱：
3 4
5 6

词：
我爱你呀
```

对应：

```text
3 → 我
4 → 爱
5 → 你
6 → 呀
```

### 8.5 延音不消耗歌词

例如：

```text
3 - -
我
```

应理解为：

```text
3 → 我
- → 延续“我”
- → 延续“我”
```

不能把两个 `-` 当成新的歌词位置。

### 8.6 休止不消耗歌词

例如：

```text
3 0 4
我   爱
```

表示：

```text
3 → 我
0 → 休止
4 → 爱
```

### 8.7 歌词数量不足

仅当用户实际提供了至少一个歌词 token 时，才校验歌词数量。

歌词为空或只包含空白时，视为未提供歌词：不产生 Warning，所有 `Note.lyric` 为 `null`，转换正常完成。

已提供歌词但数量不足时：

允许转换。

未匹配的 `Note.lyric` 使用 `null`。

必须产生 Warning。未匹配的音符仍然正常输出。

### 8.8 歌词数量过多

允许转换。

必须产生 Warning。

不允许静默丢弃多余歌词。多余歌词 token 必须保留在转换结果中，并在 Warning 中明确展示给用户。

---

## 9. 输出要求

V1 默认输出文字版字母简谱。

输出必须保留：

- 音符顺序
- 音区映射结果
- `0`
- `-`
- `|`
- 歌词信息

输出应尽可能保持输入的谱面结构。

示例：

```text
数字简谱：
3 3 3 4 5 | 3 2 2

歌词：
黑黑的天空低垂

输出：
D D D F G | D S S
黑 黑 的 天 空 | 低 垂
```

---

## 10. 错误处理

程序不得静默忽略无法识别的输入。

例如：

```text
3 4 ABC 5
```

应明确指出存在无法识别的内容。

V1 不支持的语法也必须明确告诉用户。

错误必须包含：

- 行号 `line`
- 真实字符列号 `column`
- token 顺序 `tokenIndex`
- 原始 token
- 错误原因

`column` 必须是源文本中的真实 1-based 字符列号。如果需要保存 token 顺序，使用独立的 `tokenIndex` 字段，不得把 `column` 复用为元素序号。

用户可见错误仍可使用 token 顺序描述，例如：

```text
第 3 行第 8 个元素无法识别：1#
```

其中「第 8 个元素」对应 `tokenIndex`，不是 `column`。

禁止只显示“转换失败”而不给出定位信息。

---

## 11. 输入容错

V1 应对以下情况保持基本容错：

- 多个空格
- Tab
- 前后空格
- 空行
- 连续中文歌词
- 空格分隔歌词

但是：

> 格式可以宽容，语义必须严格。

不得因为“看起来像”而自动猜测非法简谱。

---

## 12. 用户体验

V1 的典型流程：

```text
粘贴数字简谱
      ↓
可选粘贴歌词
      ↓
点击「转换」
      ↓
查看字母简谱
      ↓
点击「复制」
```

编辑输入不得自动执行完整转换，也不得自动刷新输出区。

点击「清空」应清空：

- 数字简谱输入
- 歌词输入
- 转换结果
- 错误状态

---

## 13. 复制功能

点击“复制”后，将当前字母简谱完整复制到系统剪贴板。

复制内容应包含：

- 字母简谱
- 有歌词时包含歌词
- 小节线
- 休止符
- 延音符

复制结果应与输出区显示一致。

如果当前没有可复制结果，应给予明确提示。

---

## 14. 核心数据模型

禁止采用“整段字符串大量 replace 后直接输出”的方式作为正式实现。

必须建立统一结构化数据模型。

V1 使用现有结构化模型，不引入 `Measure` 对象：

```text
Score
ScoreLine
Note
Rest
Hold
MeasureBar
Lyric
```

逻辑关系：

```text
原始输入
↓
点击「转换」
↓
Tokenizer
↓
Parser
↓
Structured Score
↓
Lyric Alignment
↓
Validate
↓
Keyboard Mapping
↓
Renderer
```

---

## 15. 模块职责

### Parser

负责：

- token 识别
- 数字音符识别
- 音区识别
- 休止识别
- 延音识别
- 小节线识别
- 结构化数据生成
- 解析错误

### Mapping

负责：

```text
数字音符 + 音区
↓
键盘字母
```

### Lyric Alignment

负责全局顺序对齐：

```text
全部可消费 Note 序列
↔
全部歌词 token 序列
```

不按行重置。换行、`0`、`-`、`|` 都不消费歌词。

### Renderer

负责：

```text
结构化数据
↓
字母简谱文本
```

### UI

负责：

- 输入
- 输出
- 按钮
- 状态展示
- 错误提示
- 复制

UI 不负责实现 Parser。

---

## 16. 非功能需求

### 跨平台

核心逻辑尽量共享。

### 可测试

Parser、Mapping、Lyric Alignment、Renderer 必须可以独立测试。

### 可扩展

未来可以添加：

- 图片识谱
- 播放
- 自动按键
- MIDI
- 鼠标
- 自定义 Mapping

而无需重写核心 Parser。

### 可维护

模块职责必须清晰，避免创建一个“什么都负责”的 Manager。

---

## 19. 产品设计原则

1. 简谱转换是核心功能。
2. 歌词对应是核心功能之一。
3. UI 输入与内部数据模型必须分离。
4. 文字输入和未来图片输入必须共用统一数据模型。
5. 键位映射必须独立。
6. 自动按键不能污染 Core。
7. 不为了未来功能让 V1 变复杂。
8. 优先正确性，其次才是视觉和性能。
